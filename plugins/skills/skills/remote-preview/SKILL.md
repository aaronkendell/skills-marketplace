# Remote Preview — Share local mocks via Cloudflare tunnels

Use this skill whenever you generate a mock, preview, or brainstorming server that the user might want to review from another device or off-network. It wraps `cloudflared tunnel --url http://localhost:PORT` so each invocation creates an independent ephemeral `*.trycloudflare.com` URL. No account required.

Two entry points:

- **`host.sh <file-or-dir>`** — you have a static file (e.g. `design-showcase.html`) and want a public URL in one call. Spins up `python3 -m http.server` on a free port AND the tunnel.
- **`share.sh <port>`** — you already have a dev server running on a known port and just need the tunnel.

## When to offer this

Offer to share a preview whenever:

- A design skill (`ui-ux-pro-max`, `shadcn`, `remotion-best-practices`, `playwright-cli`) produces HTML/component mocks on a local port
- A brainstorming or agent dev server is running locally
- The user mentions reviewing from phone, iPad, or off-network
- A mock needs approval before you continue

**Do not silently share.** Always confirm with the user before creating a tunnel. Public tunnels expose your localhost; only share what is safe to expose.

For **stable, named** tunnels on `bokendell.com` (dev APIs, Expo), use `swarm tunnel` / `swarm dev --tunnel` instead — this skill is for throwaway previews.

## Before Starting: Check for Active Workspace

If you are inside a workspace worktree (`.workspace.json` exists in CWD or a parent), the named tunnel on `*.dev.bokendell.com` is already configured. Use workspace tunnel URLs instead of creating a new quick tunnel:

```bash
# Check for active workspace
cat .workspace.json 2>/dev/null
```

If `.workspace.json` is found, prefer `https://<app>-<workspace-name>.dev.bokendell.com` over starting a new `trycloudflare.com` tunnel. The named tunnel is stable, always-on, and works even on Tailscale Wi-Fi (where `trycloudflare.com` URLs are blocked by Tailscale DNS).

If no `.workspace.json` exists (not in a workspace), proceed with the quick tunnel commands below.

## Prerequisites

- `cloudflared` installed (`brew install cloudflared` or `winget install Cloudflare.cloudflared`)
- The local service is already running on a known port

Check once:

```bash
scripts/check.sh
```

If it errors, stop and ask the user to install `cloudflared`.

## Commands

All scripts live in `scripts/` relative to this skill. Run with the port or label as an argument.

### Host a static file or directory (one-shot)

```bash
bash scripts/host.sh <file-or-dir> [label] [port]
```

Use this for HTML mocks, design showcases, decision mocks, SVG exports, or anything that doesn't need a real dev server. In one call it:

1. Picks a free local port (or uses the one you pass)
2. Starts `python3 -m http.server --bind 127.0.0.1` rooted at the file's parent dir
3. Calls `share.sh` to start a cloudflared tunnel on that port
4. Appends the filename (if `<path>` is a file) so the URL points directly at the mock
5. Prints the public URL on the last line

Example — sharing a decision mock generated by `/dev research`:

```bash
bash scripts/host.sh docs/apps/golf/planning/course-search-redesign/design-showcase.html "course-search-mock"
# → https://devoted-infinite-hitachi-facts.trycloudflare.com/design-showcase.html
```

Both the HTTP server and the tunnel are tracked in the state file; `stop.sh <label>` kills both.

**When to use `host.sh` vs `share.sh`:** if the thing being shared is already running (Next.js dev server, Expo web, shadcn preview, Remotion studio, etc.), use `share.sh`. If it's a plain HTML file sitting on disk, use `host.sh` — no need to pre-run a server. `host.sh` binds to `127.0.0.1` only so the content is reachable exclusively through the tunnel.

### Start a tunnel for an already-running port

```bash
bash scripts/share.sh <port> [label]
```

- `<port>`: local port to expose (e.g. `3000`)
- `[label]`: optional short name (e.g. `ui-mock-dashboard`) — shown in list output

Prints the public URL on success and records it in `/tmp/claude-remote-preview/tunnels.json`.

Example:

```bash
bash scripts/share.sh 3000 "shadcn-login-preview"
# → https://random-three-words.trycloudflare.com
```

### List active tunnels

```bash
bash scripts/list.sh
```

Shows every tunnel this skill has started, with label, port, URL, PID, and whether the process is still alive.

### Stop a tunnel

```bash
bash scripts/stop.sh <port|label|--all>
```

Kills the cloudflared process for that tunnel and removes it from the registry.

## Workflow

**Static HTML mock (most common for `/dev research`, brainstorming, decision mocks):**

1. You generate a `.html` file in the repo (e.g. `docs/apps/golf/planning/foo/design-showcase.html`).
2. Ask: *"Want me to put this on a public URL so you can tap through it on your phone?"*
3. On yes, run `bash scripts/host.sh <path-to-html> "<short-label>"` — no need to start any server first.
4. Hand the URL (last line of stdout) to the user. It already includes the filename suffix.
5. Keep working; the Python http.server and tunnel stay up until `stop.sh <label>`.

**Already-running dev server (shadcn preview, Next.js, Remotion, Expo web):**

1. The server is running on port N (confirmed via the command that started it).
2. Ask before tunneling.
3. Run `bash scripts/share.sh N "<short-label>"`.
4. Wait for the URL (script blocks up to ~20s).
5. Hand URL to user.

**Session cleanup (IMPORTANT):**

Tunnels do not self-expire — they stay up until `stop.sh` kills them or cloudflared itself dies. **You are responsible for tearing down tunnels you created before the session ends.** The workflow:

- If the user generates another mock in the same session, run `host.sh` or `share.sh` again with a different label — each call gets its own URL. Old tunnels keep running in parallel.
- **Before the final message in a turn where you started tunnels and the preview is no longer needed**, run `bash scripts/stop.sh --all` (or per-label) as one of your last tool calls. Never leave orphaned cloudflared or Python http.server processes behind.
- If you started a tunnel for a mid-conversation preview and the user has confirmed the mock looks good / approved the design, tear it down — the PR, not the tunnel, is the artifact.
- If the user explicitly said "keep it running so I can look again later", leave it up and announce that you left it active with the label, so they can `stop.sh` later.
- At session start, run `bash scripts/list.sh` if you suspect stale tunnels from a prior crashed session and offer to clean them up.

Optional hardening: a `SessionEnd` hook in `.claude/settings.json` that runs `bash .claude/skills/remote-preview/scripts/stop.sh --all` will make teardown automatic even if I forget or the conversation crashes. This is opt-in — ask before editing settings.

## Lessons learned

- **Cloudflared works from sandboxed environments.** Even when Bash's localhost calls are blocked (can't curl your own Python server), the outbound tunnel from cloudflared still establishes — you just can't smoke-test locally first. If you need to verify from the sandbox, use `dig +short <host>` to get a Cloudflare edge IP, then `curl --resolve host:443:ip ...`.
- **`--config /dev/null` is mandatory for quick tunnels.** If the user has `~/.cloudflared/config.yml` (e.g. from `swarm tunnel init`), cloudflared silently applies its ingress rules to `--url` quick tunnels too. Any hostname not matching an ingress rule gets caught by the catchall and cloudflared returns its own 404 without ever reaching the origin. `share.sh` passes `--config /dev/null` to guarantee quick tunnels are isolated from the user's named-tunnel config.
- **Use `http://127.0.0.1:PORT`, not `http://localhost:PORT`.** On macOS `localhost` can resolve `::1` first, and most dev servers (Python http.server `--bind 127.0.0.1`, Next.js, Metro) only listen on IPv4.
- **Always bind `127.0.0.1`, not `0.0.0.0`.** `host.sh` does this so the only path to the content is through cloudflared — nothing on your LAN can accidentally find the file.
- **Label matters.** It's how `stop.sh` identifies what to kill, and `host.sh` uses it to name the state record when attaching the HTTP-server PID. Use a short kebab-case tag like `course-search-mock`, not the full filename.
- **`stop.sh` now kills both PIDs.** Previously it only killed cloudflared and orphaned the Python http.server PID from `host.sh` — fixed. Always check `list.sh` after stopping to confirm nothing was left behind.
- **Port collisions.** If a previous run crashed, `pick_port()` grabs a new random high port, but a manually-passed port can collide with a stale process. `stop.sh --all` clears the state; if a port is still in use, wait for TIME_WAIT (~30s on macOS) or pick another.
- **share.sh has a metrics-based self-check.** After connecting, it reads `http://127.0.0.1:<metrics-port>/metrics` from cloudflared to confirm requests are reaching it. If cloudflared total_requests is non-zero but all responses are 404 with zero origin errors, it warns about the ingress-config-leak signature.

## Related tooling: `swarm tunnel` for stable, authenticated tunnels

`remote-preview` is for **throwaway, public** previews. For dev APIs and Expo dev clients you use day to day, prefer **`swarm tunnel`** / **`swarm dev --tunnel <app>`** (in this monorepo's CLI). Those give you:

- Named `*-dev.bokendell.com` URLs (stable, bookmarkable on your phone)
- Cloudflare Access gates (email/SSO) so random strangers can't hit your API
- Automatic patching of `EXPO_PUBLIC_API_URL` / `NEXT_PUBLIC_*_URL` / `TUNNEL_URL` into `process.env` before turbo spawns, so the Expo client on your phone hits the tunneled API instead of `localhost`
- Infisical-compatible: wrap with `infisical run -- pnpm swarm dev --tunnel <app>` and the CLI patches env vars AFTER Infisical injects them but BEFORE the dev server starts

See `docs/context/patterns/remote-tunnels.md` for full setup (one-time `swarm tunnel init --app <id>`, CORS allowlist updates, Cloudflare Access rules).

## Risks — remind the user

- Tunnels are **public**. Anyone with the URL can hit your localhost.
- Do not expose anything with real secrets, write access, or prod data.
- `trycloudflare.com` URLs are logged in Cloudflare; treat them as public.
- Websocket support works but HMR may reconnect slowly over the tunnel.
- Free quick tunnels have no auth — for gated sharing use `swarm tunnel` with Cloudflare Access instead.

## State file

`/tmp/claude-remote-preview/tunnels.json` — JSON array of `{pid, port, label, url, startedAt}`. Safe to delete; `list.sh` rebuilds from it.
